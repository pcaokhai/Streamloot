# Design: Full Rust Rewrite of downloader-py

Generated by /office-hours on 2026-09-15
Branch: master
Repo: downloader-py (no remote)
Status: DRAFT
Mode: Builder

## Problem Statement

`downloader-py` is ~2,330 lines of hand-written Python (plus ~590 lines of tests)
across three entrypoints (CLI, FastAPI, pywebview desktop), a dynamic plugin
factory, four site extractors, a SQLite history service, and shared `utils/`
(`logger.py` alone is 155 lines). The question on the table: rewrite it in Rust.

The stated goal is a portfolio artifact — something to show freelance clients.
That, not performance and not distribution, is the bar every decision below is
measured against.

## What Makes This Cool

Two things carry the project, and neither is the download logic.

**The plugin factory degrades to nothing.** `extractors/factory.py` scans
`plugins/` at runtime, wraps each import in its own try/except, and falls back to
`YtDlpDefaultExtractor` when a plugin is absent or broken. Delete the whole
`plugins/` directory and the app still works. In Rust this becomes an explicit
architectural choice — static registration via `inventory`/`linkme` vs. dynamic
`libloading` — and the tradeoff is worth writing down.

**One core, three faces.** `core/` and `downloaders/` never touch UI. Progress
crosses the boundary as `progress_callback(data: dict)` and nothing else. The CLI
renders it with `rich`, the API streams it as SSE, the desktop app bridges it into
a webview. In Rust that seam becomes a typed `tokio::sync::broadcast` channel of a
`ProgressEvent` enum, which is strictly better than a dict and reads as a deliberate
design, not an accident.

## Constraints

- **Solo, weekends.** No team, no deadline, but also no tolerance for a port that
  stalls at 60% — a half-finished Rust repo is worse for the stated goal than the
  finished Python one.
- **Two foreign binaries stay.** `yt-dlp` is spawned as a subprocess; Chromium is
  driven over CDP. Neither becomes Rust. The rewrite is of the ~2,330 lines around
  them.
- **Four plugins, 315 lines.** `youtube.py` plus three private site
  extractors (gitignored via the `*_private.py` convention in `.gitignore`).
  Three of the four require the browser path.
- **macOS primary.** Cross-compilation is optional scope.

## Premises

Agreed during the session, except where noted.

1. **The bar for a portfolio piece is "finished," not "impressive tech."** A
   complete Python app beats a 60%-ported Rust one. Nobody clones a half-rewrite.
   This is the premise the staging plan below exists to protect.

2. **This repo cannot be shown to clients as-is, in any language.**
   The three private site extractors under `plugins/` are in the
   directory `CLAUDE.md` points at as where the interesting work lives. Rust does
   not fix this. It is a ~10-minute fix and it is a hard prerequisite, not a
   nice-to-have — see Dependencies.

3. **The architecture is the portfolio story, not the code.** Three entrypoints
   over one UI-free core, a self-healing plugin factory, a clean progress
   boundary. That reads well in any language and is currently written down
   nowhere a client would look.

4. **Rust's genuine win here is distribution, and it is partial.** A single signed
   binary replaces the pywebview + uvicorn + random-API-key + CORS contraption in
   `apps/desktop/main.py`. But `yt-dlp` and Chromium still ship alongside it, so
   "single binary" describes the executable, not the app bundle.

5. **The Chromium plugins are the port's real cost, and the reason it stalls.**
   `chromiumoxide` drives CDP competently. It does not carry DrissionPage's
   anti-detection posture. Porting those three plugins is a Cloudflare-bypass
   research project wearing a porting-task costume, and the work is invisible on a
   resume — a scraper that works looks the same either way. **This premise was
   raised and the full rewrite was chosen anyway.** The staging plan below
   sequences it last for that reason.

## Approaches Considered

Three alternatives were ruled out during the session:

- **Tauri shell, keep the Python core** (recommended at the time) — Rust owns the
  desktop shell and process supervision, Python stays the extraction engine as a
  sidecar. Rejected: user wants the full language experience in the repo, not a
  seam. Note this rejects *Tauri-wrapping-a-Python-sidecar*, not Tauri itself —
  Tauri returns in Stage 3 as the native shell over a Rust core.
- **Rust download engine only** — port `downloaders/ytdlp.py`, leave the rest.
  Rejected: that file's runtime is pure subprocess wait, so the gain is zero and
  a reviewer would notice.
- **No Rust; fix the portfolio problem instead** — rename/gitignore the plugins,
  neutral demo plugin, packaging, README. Rejected as the whole project, but P2
  survives as a prerequisite regardless.

### Approach A: Full Rust rewrite (selected)

Port `core/`, `downloaders/`, `services/`, `extractors/`, `plugins/`, and all
three entrypoints to Rust. Keep `yt-dlp` and Chromium as external processes.

- **Effort:** human ~6-10 weeks of weekends / CC ~2-3 days
- **Risk:** High — concentrated entirely in the browser plugins (P5)
- **Reuses:** The architecture itself. Module boundaries, the callback seam, the
  factory's fallback semantics, and the existing SQLite schema all port directly.

## Recommended Approach

Approach A, staged so that P1 holds at every stage boundary.

The governing rule: **each stage ends with a runnable artifact you could show
someone.** No stage leaves the repo in a state where Rust is half-arrived. The
Python app stays on `master` and remains the working app until Stage 4 lands.

### Stage 0 — Prerequisite (P2)

Before any Rust. Neutralize the plugin directory: rename the three site plugins to
generic identifiers, or move them out of the repo and gitignore the path, and add
one neutral demo plugin that exercises the same extractor interface. Without this,
every later stage produces an artifact you still cannot send anyone.

### Stage 1 — Core + downloader

`core/models.rs` (`VideoInfo`), the `Extractor` and `Downloader` traits, and the
`yt-dlp` subprocess wrapper with stdout progress parsing.

- Maps: `core/models.py`, `core/downloader.py`, `core/extractor.py`,
  `downloaders/ytdlp.py` (321 lines, the largest single file)
- Crates: `tokio`, `serde`, `anyhow`/`thiserror`
- The `progress_callback(dict)` seam becomes a `ProgressEvent` enum on a
  `tokio::sync::broadcast` channel
- **Logging:** port `utils/logger.py` (155 lines) here as a thin `tracing` +
  `tracing-subscriber` setup. Every later stage depends on it.
- **Tests:** port `tests/test_ytdlp_formats.py` and `test_text_utils.py` first —
  they pin the stdout-parsing contract, which is the part most likely to drift
  during the port. Unit tests live in-module (`#[cfg(test)]`).
- **Artifact:** a binary that downloads a YouTube URL and prints progress. This
  alone is showable.

### Stage 2 — CLI + history

Port `services/download_service.py` (270 lines, including cancel/pause), 
`services/history_service.py` (247 lines), and the CLI entrypoint.

- Crates: `clap`, `indicatif` (the `rich` progress equivalent), `sqlx` or
  `rusqlite` against the existing schema
- Cancellation moves from `Popen` handle juggling to `tokio::select!` +
  `CancellationToken` — a genuine improvement worth calling out in the README
- **Database continuity:** point the Rust build at the *same* `db/` SQLite file
  and schema. No migration, no reset — the Python app and the Rust binary read
  and write the same rows during the whole transition, which is what lets
  `master` stay green (P1). If a schema change becomes necessary, add columns,
  never rename.
- **Tests:** port `test_download_service_cancel.py` and
  `test_history_service_tasks.py`. Cancellation is the behavior most likely to
  break under the `tokio::select!` rewrite.
- **Artifact:** feature-parity CLI with persistent history.

### Stage 3 — API + desktop

Port `apps/api/main.py` (349 lines) and `apps/desktop/main.py`.

- Crates: `axum` (SSE is first-class), `tauri`
- **How they compose:** the axum server stays. It is the Chrome extension's API
  and it does not go away just because the desktop app exists. Tauri embeds it on
  a loopback port exactly as `apps/desktop/main.py` embeds uvicorn today, and the
  webview talks to the Rust core over Tauri IPC rather than HTTP. IPC replaces
  the *desktop app's* use of the HTTP API, not the API itself — which is why the
  random-API-key and CORS dance disappears while the endpoints stay.
- Tauri collapses the pywebview + uvicorn + `secrets.token_urlsafe` + CORS
  allowlist stack in `apps/desktop/main.py` into IPC commands. This is the single
  most legible simplification in the whole port — make sure the README shows the
  before and after.
- **Tests:** port `test_api_formats.py`, `test_api_cancel.py`,
  `test_api_pause_resume.py` against the axum handlers.
- **Artifact:** double-clickable app. This is the portfolio centerpiece.

### Stage 4 — Plugins (the risk)

Port the extractor factory and the plugins last, when everything else is done and
the project is already showable.

- `extractors/factory.py`'s runtime scan has no direct Rust analogue. Decide
  explicitly: `inventory`/`linkme` compile-time registration (simpler, loses the
  "delete the folder" property) vs. `libloading` dynamic `cdylib` plugins
  (preserves it, unsafe FFI, ABI-fragile). Document the choice — it is the most
  interesting architectural decision in the port.
- `extractors/base_browser.py`'s process-wide `_browser_lock` (already marked
  with a `ponytail:` comment) becomes a `tokio::sync::Semaphore`, which supports
  real pooling rather than serializing everything.
- The Cloudflare-bypass behavior in the three browser plugins is where the
  schedule dies. Timebox it. If `chromiumoxide` cannot reach parity in the
  timebox, ship Stage 3 with the default `yt-dlp` extractor plus the neutral demo
  plugin and mark browser extraction as future work — the factory's fallback
  design makes that a supported state, not a broken one. **That is the exit ramp
  that keeps P1 intact.**
- **Tests:** `test_extractor_factory.py` and `test_plugin_resilience.py` port
  directly and are the ones that matter most — they assert the "delete
  `plugins/` and it still works" property, which is the whole architectural
  story.

## Open Questions

1. **Static or dynamic plugin registration?** Decide at the start of Stage 4, not
   during it. The "delete `plugins/` and it still works" property is the repo's
   best architectural story; `inventory` drops it, `libloading` keeps it at the
   cost of unsafe FFI.
2. **Does `chromiumoxide` clear Cloudflare on these targets?** Unverified.
   Cheapest possible probe: one throwaway Rust binary that opens a protected page
   and reports whether it lands. Run it before Stage 1, not before Stage 4 — it
   costs an afternoon and it decides whether Stage 4 exists at all.
3. **`sqlx` or `rusqlite`?** `sqlx` gives compile-time-checked queries (nice to
   show); `rusqlite` is lighter and bundles more easily into a Tauri app.
4. **Cross-platform builds?** macOS only, or does the portfolio value increase
   enough to justify Windows/Linux CI?
5. **Landscape unverified.** The Rust ecosystem claims here (`chromiumoxide`
   maturity, Tauri sidecar behavior) come from in-distribution knowledge — no web
   search was run this session.

## Success Criteria

- Stage 3 ships a double-clickable macOS app that downloads a video with visible
  progress.
- The repo can be linked to a client without a caveat (Stage 0).
- `README.md` carries the architecture diagram and the `apps/desktop/main.py`
  before/after. The architecture story is written down, not just implemented.
- Python `master` stays green until Rust reaches parity. No dead intermediate state.
- Each stage lands with its ported tests passing. The existing suite (11 files,
  ~590 lines) is the parity oracle for the whole port — it is the cheapest
  possible check that the Rust build actually does what the Python one did.

## Distribution Plan

- **Channel:** GitHub Releases, `.dmg` via Tauri bundler, plus `cargo install`
  for the CLI. Caveat: `cargo install` will not bundle or fetch `yt-dlp`, so CLI
  users need it already on `PATH`. Either document that prerequisite and fail
  with a clear message when the binary is missing, or drop the cargo channel and
  ship only the bundled app.
- **CI:** GitHub Actions on tag — `cargo test`, `cargo clippy`, `tauri build`,
  attach artifacts. Set this up during Stage 2, not at the end; a green CI badge
  is itself a portfolio signal, and retrofitting release automation is the step
  that usually gets skipped.
- **Signing:** unsigned builds trigger Gatekeeper warnings, which undercuts the
  "double-clickable app" claim. Decide whether an Apple Developer account is in
  scope before Stage 3.

## Dependencies

- **Stage 0 blocks the portfolio goal entirely.** Do it first; it is ~10 minutes.
- The `chromiumoxide` Cloudflare probe (Open Question 2) should run before Stage 1
  so Stage 4's feasibility is known early rather than discovered late.
- Apple Developer account, if signed builds are in scope.

## What I noticed about how you think

- You asked "could this be rewritten in Rust," not "should I." The framing was
  already open to the answer being no, which is why the P2 finding landed instead
  of getting argued with.
- You picked the full rewrite immediately after reading that it has "the highest
  odds of stalling at 60%." You read the con and took it anyway. That is a
  legitimate call when the goal is the experience of doing it — but it means the
  staging plan above is the part of this doc that matters, not the crate list.
- The `ponytail:` comment on `_browser_lock` in `extractors/base_browser.py`
  names its own ceiling and upgrade path. Whoever wrote that was thinking about
  the next reader. That habit is worth more in a portfolio than the language the
  code is written in.
